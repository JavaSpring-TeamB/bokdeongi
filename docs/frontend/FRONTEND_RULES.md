# 복덩이(Bokdeongi) — 프론트엔드 개발 규칙

**문서명:** FRONTEND_RULES.md
**버전:** v1.0
**작성일:** 2026-11-12
**적용 범위:** 전체 프론트엔드
**개발 환경:** IntelliJ IDEA / HTML5 Boilerplate
**기술 스택:** HTML5, CSS3, Vanilla JavaScript

---

## 1. 문서 목적

본 문서는 복덩이 프로젝트의 프론트엔드 개발 방식과 코드 작성 기준을 정의한다.

Codex 및 모든 프론트엔드 개발자는 코드 작성, 수정, 리팩터링 전에 본 문서를 확인해야 한다.

### 핵심 원칙

1. HTML, CSS, JavaScript의 역할을 명확하게 분리한다.
2. 공통 UI와 공통 스타일을 재사용한다.
3. 파일명, 클래스명, 함수명 등 네이밍 규칙을 통일한다.
4. 기존 프로젝트 구조와 설정을 유지한다.
5. 사용자가 요청하지 않은 페이지나 기능을 임의로 생성하지 않는다.
6. 백엔드 REST API 연동을 고려하여 코드를 작성한다.
7. 중복 코드와 불필요한 외부 의존성을 최소화한다.
8. 모든 페이지에 디자인 가이드와 접근성 규칙을 적용한다.
9. 코드 변경 후 기존 기능이 정상적으로 동작하는지 확인한다.
10. 실제로 검증하지 않은 기능을 완료된 것으로 보고하지 않는다.

**최종 목표: 유지보수가 쉽고, 공통 디자인이 일관되며, Spring Boot 백엔드와 통합하기 쉬운 프론트엔드 구현.**

## 2. 프로젝트 개발 환경

### 2.1 기본 환경

| 항목 | 내용 |
|---|---|
| IDE | IntelliJ IDEA |
| 프로젝트명 | bokdeongi |
| 프로젝트 유형 | HTML5 Boilerplate |
| HTML | HTML5 |
| CSS | CSS3 |
| JavaScript | Vanilla JavaScript |
| 백엔드 | Spring Boot (별도 개발) |
| 데이터베이스 | PostgreSQL (별도 개발) |
| 통신 | REST API |
| 버전 관리 | Git / GitHub |

### 2.2 기술 사용 제한

다음 기술은 별도 승인 없이 추가하지 않는다.

- React
- Vue
- Angular
- Bootstrap
- jQuery
- TypeScript
- 불필요한 UI 라이브러리
- 추가 CSS 프레임워크

현재 프로젝트의 기존 의존성은 먼저 확인하고 유지한다.

필요성이 명확하지 않은 패키지는 설치하지 않는다.

### 2.3 기존 설정 유지

HTML5 Boilerplate에서 생성된 설정 파일을 임의로 삭제하거나 변경하지 않는다.

특히 다음 파일은 기존 내용을 확인한 후 필요한 경우에만 수정한다.

- `package.json`
- `webpack.common.js`
- `webpack.config.dev.js`
- `webpack.config.prod.js`
- `.gitignore`
- `.editorconfig`

실제 파일이 존재하는지 확인하고, 존재하지 않는 파일은 임의로 생성하지 않는다.

프로젝트의 실행 및 빌드 방식은 기존 설정을 우선한다.

| 폴더 | 역할 |

| `js/` | 공통 및 페이지별 JavaScript |
| `img/` | 캐릭터, 로고, 배너 등 이미지 |

### 3.3 파일 관리 규칙

- 기존 폴더명 변경 금지
- 기능이 없는 빈 파일 생성 지양
- 동일한 목적의 파일 중복 생성 금지
- 기존 파일 전체를 무분별하게 재작성하지 않는다
- 사용하지 않는 파일이라도 임의 삭제하지 않는다
- 프로젝트 루트에 불필요한 임시 파일을 생성하지 않는다
- 테스트용 코드는 실제 서비스 코드와 구분한다

## 4. 파일명 규칙

### 4.1 기본 원칙

- 파일명은 영어 소문자 사용
- 단어 구분은 하이픈(`-`) 사용
- 공백과 한글 파일명 지양
- 파일명을 통해 페이지 또는 기능을 알 수 있도록 작성
- 동일한 목적의 파일은 동일한 이름 체계를 사용

### 4.2 HTML 파일명

HTML 파일명은 `PAGE_SPEC.md`에 정의된 경로를 따른다.

예시:

```text
index.html
login.html
benefit-list.html
benefit-detail.html
benefit-recommend.html
application-status.html
easy-translator.html
my-page.html
```

페이지별 검색 결과, 로딩, 오류 등의 상태를 위해 별도 HTML 파일을 만들지 않는다.

### 4.3 CSS 파일명

```text
common.css
home.css
benefit-list.css
benefit-detail.css
application-status.css
```

### 4.4 JavaScript 파일명

```text
common.js
home.js
benefit-list.js
benefit-detail.js
application-status.js
```

페이지별 CSS와 JavaScript는 가능한 한 동일한 기본 이름을 사용한다.

## 5. HTML 작성 규칙

### 5.1 기본 원칙

- HTML5 표준을 따른다.
- 시맨틱 태그를 사용한다.
- HTML은 화면 구조와 콘텐츠를 담당한다.
- CSS 스타일을 HTML에 직접 작성하지 않는다.
- 복잡한 JavaScript를 HTML에 직접 작성하지 않는다.
- 중복 마크업을 최소화한다.
- 접근성을 고려한 구조로 작성한다.

### 5.2 기본 문서 구조

```html
<!DOCTYPE html>
<html lang="ko">
<head>
  <meta charset="UTF-8">
  <meta name="viewport"
        content="width=device-width, initial-scale=1.0">
  <title>복덩이</title>

  <link rel="stylesheet" href="css/common.css">
  <link rel="stylesheet" href="css/home.css">
</head>

<body>
  <header>
    <!-- 공통 헤더 -->
  </header>

  <main>
    <!-- 페이지별 콘텐츠 -->
  </main>

  <footer>
    <!-- 공통 하단 영역 -->
  </footer>

  <script src="js/home.js" defer></script>
</body>
</html>
```

위 코드는 기본 구조 예시다.

실제 프로젝트에 Webpack 등 빌드 도구가 설정되어 있다면 기존 진입점과 리소스 로딩 방식을 먼저 확인한다.

기존 설정과 충돌하는 방식으로 CSS 또는 JavaScript를 중복 연결하지 않는다.

### 5.3 HTML 태그 사용

| 용도 | 태그 |
|---|---|
| 공통 헤더 | header |
| 내비게이션 | nav |
| 메인 콘텐츠 | main |
| 콘텐츠 구역 | section |
| 독립 콘텐츠 | article |
| 부가 정보 | aside |
| 페이지 하단 | footer |
| 버튼 동작 | button |
| 페이지 이동 | a |
| 사용자 입력 | form, input, select |

### 5.4 제목 계층

- 페이지의 주제는 H1 사용
- 주요 콘텐츠 구역은 H2
- 카드 및 하위 영역은 H3
- 제목 계층을 장식 목적으로 변경하지 않는다

글자 크기 및 굵기는 `DESIGN_GUIDE.md`를 따른다.

### 5.5 HTML 제한 사항

- 인라인 스타일 사용 지양
- `onclick` 등 인라인 이벤트 속성 사용 금지
- 의미 없는 div 남용 지양
- 페이지 이동에 button 태그만 사용하는 방식 지양
- 클릭할 수 없는 요소에 버튼처럼 보이는 스타일 적용 금지
- 접근 가능한 이름이 없는 아이콘 버튼 사용 금지

## 6. CSS 작성 규칙

### 6.1 파일 역할 분리

**common.css**

모든 페이지에 적용되는 스타일을 관리한다.

- 색상 변수
- 글꼴
- 기본 레이아웃
- 공통 헤더
- 공통 버튼
- 공통 카드
- 입력창
- 탭
- 배지
- 반응형 공통 규칙

**페이지별 CSS**

해당 페이지에서만 사용하는 레이아웃과 스타일을 관리한다.

예시:

- `home.css`: 홈 대시보드
- `benefit-list.css`: 복지 검색
- `application-status.css`: 신청 현황

### 6.2 디자인 토큰 사용

색상, 폰트 크기, 간격, 모서리 반경 등은 디자인 가이드에서 정의한 CSS 변수를 사용한다.

예시:

```css
.home-card {
  background: var(--color-white);
  border: 1px solid var(--color-border);
  border-radius: var(--radius-lg);
  padding: var(--space-lg);
}
```

다음과 같이 임의의 값을 반복 작성하지 않는다.

```css
/* 지양 */
.home-card {
  background: #f7fff7;
  border-radius: 17px;
  padding: 23px;
}
```

### 6.3 CSS 네이밍 규칙

클래스명은 영어 소문자와 하이픈을 사용한다.

공통 클래스:

```text
.container
.site-header
.site-nav
.btn
.btn-primary
.btn-secondary
.card
.badge
```

페이지별 클래스:

```text
.home-banner
.home-summary
.home-calendar
.benefit-search
.benefit-card
.application-progress
```

페이지 전용 클래스에는 해당 페이지를 나타내는 접두어를 사용한다.

### 6.4 스타일 충돌 방지

- 페이지 CSS에서 공통 헤더 스타일을 임의로 변경하지 않는다.
- 공통 버튼 클래스를 불필요하게 덮어쓰지 않는다.
- 전역 태그 선택자를 과도하게 사용하지 않는다.
- `!important` 사용을 지양한다.
- 과도한 선택자 중첩을 피한다.
- 기존 공통 CSS를 수정할 때 다른 페이지에 미치는 영향을 확인한다.

### 6.5 반응형 CSS

반응형 구간은 `DESIGN_GUIDE.md`를 따른다.

기본 원칙:

- 고정 너비보다 유동적인 너비 사용
- Flexbox 및 CSS Grid 활용
- 모바일 가로 스크롤 방지
- 텍스트 잘림 방지
- 이미지 비율 유지
- 버튼과 입력창의 터치 영역 확보

## 7. JavaScript 작성 규칙

### 7.1 기본 원칙

- Vanilla JavaScript 사용
- 화면별 기능 분리
- DOM 조작과 데이터 처리 분리
- 이벤트 리스너 사용
- 전역 변수 최소화
- 동일한 코드 반복 지양
- 명확한 함수명 사용

### 7.2 변수 선언

기본적으로 `const`를 사용한다.

재할당이 필요한 경우에만 `let`을 사용한다.

`var`는 사용하지 않는다.

```javascript
const currentDate = new Date();
let selectedMonth = currentDate.getMonth();
```

### 7.3 함수명 규칙

함수는 역할을 알 수 있는 이름으로 작성한다.

예시:

```javascript
renderCalendar()
renderBenefitCards()
updateApplicationStatus()
handleSearch()
fetchBenefits()
```

함수명은 camelCase를 사용한다.

### 7.4 DOM 이벤트

HTML에 직접 이벤트를 작성하지 않는다.

```javascript
const nextButton =
  document.querySelector(".calendar-next");

if (nextButton) {
  nextButton.addEventListener("click", () => {
    // 다음 달 이동
  });
}
```

동작하지 않는 버튼을 단순 장식용으로 배치하지 않는다.

### 7.5 데이터와 렌더링 분리

데이터 처리 함수와 화면 표시 함수를 분리한다.

예시:

```javascript
function renderSummary(data) {
  const target =
    document.querySelector("#expected-amount");

  if (!target || !data) return;

  target.textContent =
    Number(data.expectedAmount).toLocaleString("ko-KR");
}
```

사용자 데이터와 외부 API에서 받은 텍스트는 안전하게 렌더링한다.

가능하면 `textContent`를 사용하고, 외부 입력값을 검증 없이 `innerHTML`에 삽입하지 않는다.

### 7.6 비동기 처리

실제 API 연동 시 `async/await`를 사용한다.

다음 상태를 구분한다.

- 요청 전
- 로딩 중
- 성공
- 데이터 없음
- 오류

요청 실패 시 화면 전체가 깨지지 않도록 처리한다.

## 8. Mock Data 사용 규칙

### 8.1 기본 원칙

현재 프론트엔드 개발 단계에서는 백엔드 API가 연결되지 않은 기능에 한해 Mock Data를 사용할 수 있다.

Mock Data는 UI 구현 및 테스트 용도로만 사용한다.

### 8.2 데이터 관리

- 샘플 데이터를 화면 코드와 구분한다.
- 실제 사용자 데이터처럼 표시하지 않는다.
- 금액, 신청 상태 등은 예시임을 알 수 있게 한다.
- 임의의 실제 정부 지원금 자격 판정 결과를 생성하지 않는다.
- 실제 API 연동 시 쉽게 교체할 수 있도록 구성한다.

### 8.3 데이터 구조

예시:

```javascript
const mockSummary = {
  expectedAmount: 420000,
  maxAmount: 1260000,
  isMock: true
};
```

위 숫자는 실제 복지 지원금이나 사용자 판정 결과가 아닌 UI 테스트용 예시다.

### 8.4 데이터와 UI 분리

UI 컴포넌트는 가능한 한 전달받은 데이터를 렌더링하도록 구현한다.

Mock Data를 직접 참조하는 코드가 전체 화면에 흩어지지 않도록 한다.

## 9. 백엔드 REST API 연동 준비

### 9.1 역할 분리

**프론트엔드**

- 사용자 화면 표시
- 입력값 수집
- 입력 형식 검증
- API 요청
- 응답 데이터 렌더링
- 사용자 동작 처리

**백엔드**

- 인증 및 권한 확인
- 사용자 정보 관리
- 데이터베이스 처리
- 복지 혜택 조회
- 복지 자격 판정
- 신청 상태 저장
- AI 서비스 연동

최종 자격 판정이나 민감정보 검증을 프론트엔드에서 임의로 처리하지 않는다.

### 9.2 API 호출 분리

API 연동 시 네트워크 요청 코드는 별도 모듈로 분리한다.

예시 구조:

```text
js/
├── api.js
├── home.js
├── benefit-list.js
└── application-status.js
```

현재 실제 API 명세가 확정되지 않았다면 `api.js`를 억지로 생성할 필요는 없다.

### 9.3 API 연동 원칙

- API URL 임의 확정 금지
- HTTP 메서드 임의 확정 금지
- 실제 응답 필드명 임의 확정 금지
- API 오류 처리
- 로딩 상태 표시
- 응답 데이터 유효성 확인
- 인증이 필요한 요청 구분
- 백엔드와 데이터 형식 협의

### 9.4 보안 주의사항

- 비밀번호를 localStorage에 저장하지 않는다.
- API 키 및 비밀키를 프론트엔드 코드에 포함하지 않는다.
- 민감정보를 콘솔에 출력하지 않는다.
- 인증 토큰 저장 방식은 백엔드 담당자와 협의한다.
- 개발용 사용자 데이터에는 실제 민감정보를 사용하지 않는다.
- 인증·인가 판단은 서버에서 최종 처리한다.

## 10. 공통 UI 재사용 규칙

### 10.1 재사용 대상

다음 구성요소는 페이지별로 디자인을 새로 만들지 않는다.

- 공통 헤더
- 내비게이션 메뉴
- 버튼
- 카드
- 입력창
- 검색창
- 탭
- 상태 배지
- 로딩 안내
- 오류 안내
- 빈 상태 안내

### 10.2 공통 헤더

모든 페이지는 `DESIGN_GUIDE.md`에 정의한 헤더 디자인을 따른다.

헤더 변경이 필요한 경우 개별 페이지에서 수정하지 않고 공통 구현을 수정한다.

### 10.3 HTML 재사용 방식

현재 프로젝트는 프레임워크 없는 정적 HTML 프로젝트다.

따라서 여러 페이지에서 공통 헤더를 재사용하기 위해 반드시 별도 템플릿 엔진을 도입할 필요는 없다.

공통 스타일과 동작은 CSS 및 JavaScript로 관리한다.

HTML 마크업을 여러 페이지에서 관리해야 할 경우 팀에서 승인한 공통 컴포넌트 방식으로 통합할 수 있다.

검증되지 않은 임의의 HTML include 시스템을 추가하지 않는다.

## 11. 페이지 이동 규칙

### 11.1 이동 경로

페이지 이동은 `PAGE_SPEC.md`를 따른다.

### 11.2 링크 사용

화면 이동에는 기본적으로 `a` 태그를 사용한다.

```html
<a href="benefit-list.html">
  복지 혜택 찾기
</a>
```

동작 버튼은 `button` 태그를 사용한다.

### 11.3 아직 구현되지 않은 페이지

- 존재하지 않는 페이지를 구현된 것처럼 연결하지 않는다.
- 사용자가 요청하지 않은 페이지를 임의로 생성하지 않는다.
- 필요한 경우 '준비 중' 안내를 제공한다.
- 임의의 빈 HTML 페이지를 대량 생성하지 않는다.

### 11.4 상대 경로

현재 프로젝트 루트의 HTML 파일에서 CSS, JS, 이미지는 다음과 같이 참조한다.

```text
css/common.css
css/home.css
js/home.js
img/실제파일명.png
```

향후 Spring Boot 프로젝트에 통합할 때는 백엔드 프로젝트의 정적 리소스 구조에 맞게 경로를 조정한다.

## 12. 이미지 및 에셋 관리

### 12.1 이미지 폴더

모든 프로젝트 이미지는 `img/`에서 관리한다.

### 12.2 복덩이 캐릭터

- 제공된 원본 이미지 우선 사용
- 원본 캐릭터 외형 변경 금지
- 이미지 비율 유지
- 임의의 캐릭터 대체 금지
- 불필요한 이미지 중복 저장 금지

### 12.3 배너 이미지

홈 메인 배너는 기존 배너 이미지를 사용한다.

이미지에는 배경 및 캐릭터를 사용하고, 안내 문구와 버튼은 HTML로 구현한다.

이미지 실제 비율과 배치 위치를 확인하여 캐릭터가 잘리지 않도록 한다.

### 12.4 이미지 최적화

- 이미지 크기 및 용량 확인
- 적절한 이미지 형식 사용
- 필요 시 WebP 등 최적화 형식 활용
- 접근성에 맞는 대체 텍스트 사용
- 장식용 이미지는 필요한 경우 대체 텍스트를 비워 둔다

이미지 최적화를 위해 원본을 임의 삭제하지 않는다.

## 15. 오류 및 예외 처리

### 15.1 공통 상태

2. 로딩
3. 정상 표시
4. 결과 없음
5. 조회 실패
6. 로그인 필요

### 15.2 오류 처리 원칙

- 오류가 발생해도 페이지 전체가 깨지지 않도록 한다.

- 재시도 가능한 오류에는 재시도 동작을 제공한다.
- 입력한 내용은 가능한 한 유지한다.
- 개발자용 오류 메시지를 그대로 사용자에게 표시하지 않는다.

### 15.3 빈 상태

데이터가 없는 경우 빈 영역으로 방치하지 않는다.

화면설계의 빈 상태 안내와 복덩이 캐릭터 이미지를 활용한다.

## 16. 코드 품질 규칙

### 16.1 중복 방지

- 같은 스타일을 여러 파일에 중복 작성하지 않는다.
- 반복 동작은 공통 함수로 분리한다.
- 동일 기능의 구현 방식을 페이지마다 변경하지 않는다.

### 16.2 가독성

- 역할이 명확한 변수명 사용
- 지나치게 긴 함수 분리
- 불필요한 중첩 조건문 최소화
- 임의의 축약어 사용 지양
- 들여쓰기 및 코드 포맷 통일

### 16.3 성능

- 불필요한 DOM 조회 반복 지양
- 중복 이벤트 리스너 등록 방지
- 이미지 용량 관리
- 불필요한 네트워크 요청 방지
- 사용하지 않는 코드 추가 금지

### 16.4 기존 코드 보호

기존 코드 수정 전 해당 코드의 역할을 확인한다.

공통 파일을 수정할 때는 다른 페이지에 미치는 영향을 확인한다.

문제 해결을 위해 전체 프로젝트 구조를 임의로 변경하지 않는다.

### 17.1 기본 원칙

- 다른 팀원 브랜치 변경
- 중요 설정 파일 삭제
- 대규모 파일 이동
- 데이터베이스 설정 변경
- 백엔드 프로젝트 구조 변경
- 기존 Git 이력 재작성

사용자가 별도 요청하지 않았다면 자동 커밋이나 푸시를 수행하지 않는다.

## 23. 최종 개발 원칙

복덩이 프론트엔드 개발은 다음 네 가지 기준을 항상 충족해야 한다.

**첫째, 디자인 통일성**

모든 페이지는 하나의 디자인 시스템을 공유한다.

**둘째, 코드 일관성**

같은 기능은 같은 구조와 작성 방식을 사용한다.

**셋째, 유지보수성**

화면별 코드를 분리하고 공통 코드를 재사용한다.

**넷째, 백엔드 연동 용이성**

실제 API 연결 시 기존 화면을 대규모로 재작성하지 않아도 되는 구조를 유지한다.
