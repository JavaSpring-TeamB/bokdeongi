# LLM 출력 검증 (B)

LLM이 공고 원문에서 뽑은 값을 프로그램이 직접 대조해 버리거나 점수를 매긴다 (D-57, D-58, D-59).
여기서 규칙을 확정하고 테스트 벡터(`cases.json`)를 만든 뒤 Java로 옮긴다. Java 구현도 같은 `cases.json`을 통과해야 한다.

## 파일

| 파일 | 내용 |
| --- | --- |
| `validator.py` | 정리·숫자/날짜 읽기·검증·점수 |
| `cases.json` | 공용 테스트 벡터 (Python, Java 둘 다 사용) |
| `test_validator.py` | 단위 테스트 |
| `check_gold.py` | 정답셋(C 라벨)으로 확인: 맞는 값을 버리지 않는지, 틀린 값을 잡는지 |

## 실행 (레포 루트에서)

```bash
python -m unittest discover -s data-lab/validation
python data-lab/validation/check_gold.py           # 사람 라벨이 하나도 버려지지 않아야 한다
python data-lab/validation/check_gold.py --wrong   # 일부러 틀린 값을 넣어 잡아내는 비율
```

외부 라이브러리는 쓰지 않는다 (표준 라이브러리만).

## 규칙

| 검사 | 방법 | 실패하면 |
| --- | --- | --- |
| 근거 문구 | 공백·줄바꿈·글머리 기호(○ㅇ※- 등)만 지우고 원문 필드 하나 안에 그대로 있는지 본다. 글자는 바꾸지 않는다 | 버림 |
| 숫자 | 값의 숫자가 **근거 문구 안에** 있는지 본다. 20만원·200천원·19,250원·1억 2천만원을 같은 값으로 읽는다 | 버림 |
| 날짜 | 같은 월·일이 근거에 있어야 한다. 연도가 생략되면 앞 날짜의 연도를 이어받고 월이 줄면 다음 해로 넘긴다. 근거에 연도가 아예 없으면 추정값으로 통과하고 메모를 남긴다 (DATA-04) | 버림 |
| 코드 | 같은 필드를 지원조건 코드(JA)로 만든 조건과 모순되지 않는지 (RULE만). LLM 조건의 허용 범위가 코드 범위 안이면 통과: `소득 60% 이하`는 코드 `0~75%`(JA0201+0202) 안이라 통과, `100% 이하`는 모순 | 점수 |
| 반복 | 같은 공고를 다시 돌렸을 때 같은 값인지. IN 목록 순서·숫자 표기(60/60.0)는 무시. RULE은 항상 2회 실행 (D-60) | 점수 |

- EXTRACT 출력은 `value`(반복 비교용 값)를 꼭 채운다. 값이 비면 반복 불일치로 본다
- 연간 환산 같은 계산값은 숫자 검사에 넣지 않는다 (원문에 없는 게 정상)
- 쉬운 말(EASY)은 근거 문구가 없으므로 문장 속 숫자가 모두 원문 어딘가에 있는지만 본다. 계산해서 만든 숫자(월 20만 → 연 240만)도 버린다

### 점수

`점수 = 0.4×숫자 + 0.3×코드 + 0.3×반복` (통과 1, 실패 0, 확인 못 함 0.5)

| 상황 | 점수 |
| --- | --- |
| 근거만 확인 (숫자 없는 조건, 코드·반복 없음) | 0.50 |
| 근거 + 숫자 | 0.70 |
| 근거 + 반복 일치 (숫자 없음) | 0.65 |
| 근거 + 숫자 + 반복 일치 | 0.85 |
| 전부 일치 | 1.00 |

판정 엔진은 점수가 최소 신뢰도 아래이거나 점수가 비어 있는 LLM 조건을 "조건부(확인 필요)"로 돌린다 (ELIG-01 `LOW_CONFIDENCE`).
최소 신뢰도는 0.80에서 시작한다. 0.80 이상 = 반복 일치 + 코드와 모순 없음 + 숫자나 코드 중 하나로 확인. B 조건 라벨로 칸별 오답을 센 뒤, 오답 0이고 표본이 충분한 칸만 내린다 (D-61).

## 알려진 한계

- 날짜는 시작일·종료일 역할까지는 보지 않는다. `2026. 7월 말~ 8월 말`에서 시작일을 8월로 잘못 뽑아도 8월이 근거에 있으므로 통과한다. 반복 검사가 이런 흔들림을 점수로 잡는다
- 근거 문구가 여러 필드에 걸쳐 있으면 못 찾는다 (필드를 이어 붙이지 않는다). 프롬프트에서 "한 필드 안의 연속된 문구"를 요구한다
